Why we care about model selection

  • In finance, we always have more potential predictors than we should trust
  • More predictors ⇒ more flexibility ⇒ easier to overfit
  • Also: interpretability matters (governance, auditability, model risk)

Use a quick story: adding lots of correlated macro variables makes coefficients swing wildly. Set up bias–variance framing: selection/regularization are ways to control variance.

Two different goals

  • Prediction: lower out-of-sample error
  • Interpretation: understand which predictors matter (direction + magnitude)
  • Often a trade-off: the best predictive model may be hard to explain

Stress that Chapter 6 tools can serve both goals, but you need to be honest which goal you’re optimizing for.

The core problem: \(p\) feels large

  • Suppose we have \(p\) candidate predictors
  • If we try all subsets: \(2^p\) models (explodes fast)
  • Even if you can compute them, choosing among them is the real challenge

Concrete numbers: p=20 ⇒ ~1 million subsets; p=40 ⇒ ~1 trillion. So we need smart search strategies and good selection criteria.

Three families of solutions (Ch. 6)

  1. Subset selection (choose predictors, fit least squares / GLM)
  2. Shrinkage / regularization (keep predictors, shrink coefficients)
  3. Dimension reduction (not our focus tonight)

We’ll spend most time on 1 and 2. Dimension reduction = PCA/PLS; mention later if asked.

Train/test + CV reminder (from Lecture 6)

  • One split is noisy
  • CV estimates out-of-sample performance more reliably
  • We’ll reuse CV to pick: model size, \(\lambda\), polynomial degree, spline df

Reinforce vocabulary: training vs assessment folds. Also remind: test set is held out for final check—don’t tune on it.

Subset selection: the idea

  • Goal: find a subset of predictors that “works well”
  • Fit the model only on that subset
  • Then evaluate / compare candidate subsets

Emphasize: we’re not “discovering truth,” we’re choosing a useful approximation. Subset selection is discrete: predictor is in or out.

Best subset selection (conceptual)

  • For each model size \(k\) (0, 1, 2, …, \(p\)):
    • search all subsets with \(k\) predictors
    • keep the best one (lowest RSS / highest likelihood)
  • Then choose \(k\) using a selection rule (CV, AIC/BIC, etc.)

This is the gold standard search for small p. But computationally expensive.

Stepwise selection (practical search)

  • Forward stepwise: start empty, add the best next predictor each step
  • Backward stepwise: start full, remove the worst predictor each step
  • Hybrid: allow adds/removes

Forward works when p is large but n is not huge. Backward requires fitting the full model first (so typically needs n > p).

What stepwise is (and is not)

  • It’s a greedy search (locally optimal choices)
  • It may miss the best subset
  • But it’s often “good enough” and very interpretable

Important caveat: p-values from stepwise are not honest after selection. We’re choosing a model; then inference is tricky.

How do we choose model size \(k\)?

  • We need a rule for “best” complexity
  • Option 1: CV estimate of test error
  • Option 2: information criteria (AIC/BIC)
  • Option 3: adjusted \(R^2\) (regression only)

Preview: CV is aligned with our course spine. We’ll mention AIC/BIC/adjR2 conceptually but not derive them.

Adjusted \(R^2\) (quick intuition)

  • \(R^2\) always increases when you add predictors
  • Adjusted \(R^2\) adds a penalty for complexity
  • So it can go up or down when you add a variable

This is a simple “complexity-aware” metric. But it’s still in-sample; CV is usually safer for prediction.

AIC / BIC (quick intuition)

  • Start with goodness-of-fit (likelihood)
  • Subtract a penalty for number of parameters
  • BIC penalizes complexity more than AIC

No derivations. Mention: in many business settings, BIC tends to choose smaller models (more parsimonious).

CV for model size: the clean story

  • For each model size \(k\):
    • pick a specific subset (best/stepwise) within each fold
    • evaluate on the fold’s assessment set
  • Choose \(k\) with the lowest CV error

This is subtle: selection must happen inside each resample to avoid optimistic bias. In practice, people often shortcut and still get usable results—note the tradeoff.

⚠️ Warning: selection can leak

❌ Leaky pipeline

  1. Run variable selection on the full dataset
  2. Pick the “best” predictors
  3. Then cross-validate the chosen model

✅ Clean pipeline

For each fold:

  1. Select predictors on training fold only
  2. Fit model on training fold
  3. Evaluate on held-out fold

CV error from the leaky pipeline is optimistically biased — your model looks better than it truly is.

This is one of the most common and costly mistakes in applied modeling — easy to do accidentally, hard to notice.

Concrete example: Suppose you have 200 candidate predictors and 1,000 observations. You compute correlations between each predictor and the outcome using all 1,000 rows, keep the top 20, then run 10-fold CV on those 20 predictors. This is wrong. When fold 1 is held out as your test set, the feature selection step already “saw” fold 1’s data — it wasn’t truly withheld. The CV error will be overly optimistic because the predictors were cherry-picked using information from every fold, including the one you’re pretending is unseen.

The rule: anything that “learns” from data — scaling, imputation, feature selection, dimensionality reduction — must be re-done inside each training fold only. It must never touch the held-out fold before evaluation.

Finance angle: this is the statistical cousin of look-ahead bias and backtest overfitting. A strategy that “selects” signals using the full historical window before backtesting will always look better than it performs live.

In practice with tidymodels: putting all preprocessing steps inside a recipe() and evaluating inside a workflow() with fit_resamples() handles this correctly by design — the recipe is re-fit on each training fold.

Regularization: why shrink instead of drop?

  • When predictors are correlated, least squares coefficients can be unstable
  • Shrinkage trades a little bias for a lot less variance
  • Often improves out-of-sample performance

This is the bias–variance trade. Bring back the idea: we’re controlling flexibility in a smoother way than “in/out.”

Bias–variance framing (again)

  • More flexibility ⇒ lower bias, higher variance
  • Regularization intentionally increases bias
  • …to reduce variance and improve test performance

Ridge regression: the idea

Optimization problem: \[\text{minimize} \quad \text{RSS} + \lambda \sum_{j=1}^p \beta_j^2\]

Intuition: the budget metaphor

Think of \(\lambda\) as controlling how tight the budget is for your coefficients.

\(\beta_j\) Penalty cost (\(\beta_j^2\))
0.1 0.01
1.0 1.00
2.0 4.00
  • A coefficient 10× larger costs 100× more → ridge heavily penalizes large values
  • Better to spread weight across many small \(\beta_j\)s than concentrate in a few big ones
  • As \(\lambda \uparrow\): budget tightens, all coefficients shrink toward 0 (but rarely exactly 0)

Finance framing: limited budget to allocate across predictors — ridge says spread it thin. Standardize predictors first; otherwise units distort the budget (a coefficient on income in dollars vs. thousands gets penalized very differently).

Lasso: the idea

Optimization problem: \[\text{minimize} \quad \text{RSS} + \lambda \sum_{j=1}^p |\beta_j|\]

Intuition: same budget, different penalty**

  • Lasso also has a budget \(\lambda\), but it penalizes absolute values (L1)
  • Ridge penalizes squared: \(\beta_j = 0.1\) costs \(0.01\); Lasso penalizes linear: \(\beta_j = 0.1\) costs \(0.1\)
  • Result: Lasso prefers sparse solutions (exact zeros)
    • It’s cheaper to drop a predictor entirely than shrink it a little bit
    • With high \(\lambda\): many coefficients snap exactly to 0 (automatic feature selection)

Why Lasso picks sparsity:

  • Ridge budget: spread weight thinly (many small coefficients)
  • Lasso budget: spend heavily on a few, or go to zero (binary decision)

The geometry intuition: L2 ball (ridge) is smooth; L1 diamond (lasso) has pointy corners. Sparse solutions live at the corners of the lasso budget region. But for now: intuition is “ridge shrinks, lasso sparsifies.”

Ridge vs lasso with correlated predictors

  • If predictors are strongly correlated:
    • Ridge tends to share weight across them
    • Lasso tends to choose one and zero out others
  • In finance: correlated ratios/macros are common → ridge can be very stable

Use this to motivate why ridge is often a nice first move in credit risk. But lasso is attractive for interpretability / sparse scorecards.

The tuning knob: \(\lambda\)

  • \(\lambda = 0\) ⇒ ordinary least squares / MLE
  • Large \(\lambda\) ⇒ heavy shrinkage ⇒ underfit
  • So we need to tune \(\lambda\) using CV

Translate to their earlier KNN tuning: k was our knob; now lambda is the knob.

Standardization matters

The budget principle: units shouldn’t matter

  • Remember: regularization penalizes coefficient magnitudes using your “\(\lambda\) budget”
  • If we measure one predictor in centimeters and another in miles, the “cost” is unfair
  • Example: \(\beta_{\text{centimeters}} = 100\) (in budget) vs \(\beta_{\text{miles}} = 0.001\) (tiny!)
  • Solution: Standardize all predictors to mean 0, SD 1 before fitting
    • Now \(|\beta| = 0.1\) means the same thing regardless of original units
    • Fair budget allocation

Why standardize inside folds?

  • If you standardize on the full dataset, then fit/CV on folds: you leak information
  • Each fold should “learn” its own mean/SD from training data only
  • Otherwise: CV folds know the global reference point → overly optimistic error estimates

In practice:

  • glmnet standardizes by default (good!)
  • But you must understand the leakage principle if you write custom tuning code
  • Same principle as scaling in KNN (Lecture 6)

Use the budget intuition: “We’re allocating a budget to coefficients. Units shouldn’t matter—a coefficient of 0.1 in miles should cost the same as 0.1 in centimeters. Standardization makes the penalty fair.” Then hit the leakage point: standardize inside each fold’s training data, not globally.

Why we’ll implement with glmnet

  • It’s the standard tool in R for ridge/lasso
  • Efficient + stable implementations (coordinate descent)
  • Built-in cross-validation via cv.glmnet()

Make an explicit course decision: we keep everything else base R, but glmnet is worth it. It won’t derail because the interface is simple and self-contained.

Regularization for classification too

  • Same idea works for logistic regression
  • We penalize the log-likelihood instead of RSS
  • In credit scoring: penalized logistic is a common baseline

This is the bridge to the project. We’ll use family=‘binomial’ in glmnet.

Tuning \(\lambda\) with CV: the algorithm

Pseudocode: what cv.glmnet() does

For each lambda value (high to low):
    For each fold i = 1, 2, ..., 10:
        Fit ridge/lasso on train fold i (with this lambda)
        Score on assessment fold i
        Record error
    Average error across all folds
Plot CV error vs log(lambda)
Pick lambda with lowest average error (or 1-SE rule)
  • Concept: “Which amount of shrinkage generalizes best?”
  • 1-SE rule: pick a slightly larger \(\lambda\) (more stable, simpler)

The beauty: glmnet does this loop for you. We just call cv.glmnet() once and get the plot. Focus on the output (CV curve). Students don’t need to understand the loop; they need to understand: “More lambda = more shrinkage = simpler. CV tells us which is best.”

Choosing \(\lambda\): min vs 1-SE

The CV curve gives you error and uncertainty at each \(\lambda\). Two common choices:

\(\lambda_{min}\) \(\lambda_{1se}\)
Rule Lowest mean CV error Largest \(\lambda\) within 1 SE of the min
Model Best average fit Simplest model not significantly worse
Risk May overfit the CV noise Slightly higher error, more stable

Intuition: The CV error curve is noisy. \(\lambda_{1se}\) asks: “is there a simpler model whose error is statistically indistinguishable from the best?” If yes, prefer it.

Walk through the logic: CV gives you a mean error and a standard error at each lambda. lambda_min picks the bottom of the curve. lambda_1se slides right along the curve until the error rises by one standard error — that model is “not significantly worse” but uses more regularization (fewer/smaller coefficients).

Why prefer lambda_1se in practice? The bottom of a CV curve is noisy — you might just be overfitting the folds. lambda_1se is a conservative hedge. In finance/model governance contexts, a simpler model is also easier to defend: “we deliberately chose a more parsimonious model that performed within noise of the best.”

In glmnet: both are returned automatically — lambda.min and lambda.1se. Students just need to know which to pass to predict().

Interpretability vs prediction (practical guidance)

  • If you need a simple, explainable model:
    • consider lasso (sparse) or stepwise (few variables)
  • If you need robust prediction under correlation:
    • ridge is often strong
  • Always validate with CV + a holdout test set

Make them articulate which they’re optimizing. Tie to grading rubric in project later.

Common pitfalls checklist

  • Leakage: feature selection/scaling done outside resampling
  • Tuning too many knobs on the test set
  • Treating selected-model p-values as “truth”
  • Forgetting stability (different folds → different models)

This slide is your “model risk” slide. Give them habits: always keep a test set, keep a log of choices, sanity check stability.
